# راهنمای جایگزینی نسخه‌ی قدیمی با نسخه‌ی جدید (روی سرور مشترک، با pm2)

این راهنما مخصوص وضعیت دقیق شماست: پروژه‌ی قدیمی الان با **pm2** روی یک **سرور مشترک** (که سرویس‌های دیگری هم رویش هست) اجرا می‌شود، و یک **ریپوی گیت‌هاب قدیمی** دارید که می‌خواهید آپدیتش کنید.

## ⚠️ اصل راهنما: تا آخرین لحظه چیزی را خراب نمی‌کنیم

استراتژی این راهنما «نصب کنار نسخه‌ی قدیمی، تست کامل، بعد جایگزینی» است — نه «حذف قدیمی و نصب جدید». یعنی:
- نسخه‌ی قدیمی تا مرحله‌ی آخر همچنان روشن و در دسترس می‌ماند.
- نسخه‌ی جدید را در یک پوشه‌ی **جدا** و روی یک **پورت جدا** بالا می‌آوریم و کامل تستش می‌کنیم.
- فقط وقتی از کارکردش مطمئن شدیم، جای قدیمی را می‌گیرد.
- اگر هر جای کار مشکلی پیش آمد، نسخه‌ی قدیمی دست‌نخورده مانده و می‌توانید همان‌جا متوقف شوید — چیزی برای کاربر نهایی قطع نمی‌شود.

هر دستوری که با `sudo` شروع می‌شود را با دقت بخوانید قبل از اجرا؛ روی سرور مشترک، به‌خصوص در بخش‌های فایروال/Nginx مراقب باشید فقط تنظیمات مربوط به همین پروژه را دست بزنید.

## مرحله‌ی ۰ — قبل از هر کاری: پشتیبان کامل بگیرید

روی سرور (SSH بزنید):

```bash
# جای پوشه‌ی پروژه‌ی قدیمی را با مسیر واقعی‌اش عوض کنید
OLD_DIR=/home/user/zagros-repost   # ← مسیر واقعی نصب قدیمی را اینجا بگذارید

# یک بکاپ فشرده از کل پوشه‌ی قدیمی (کد + .env.local + data/) در home بگیرید
tar -czf ~/zagros-repost-backup-$(date +%Y%m%d-%H%M).tar.gz -C "$(dirname "$OLD_DIR")" "$(basename "$OLD_DIR")"
ls -lh ~/zagros-repost-backup-*.tar.gz
```

این یک فایل فشرده می‌سازد که شامل `data/connections.json`, `data/admin.json`, `data/logs.json`, و `.env.local` قدیمی (با تمام secret ها) است. **این فایل را از سرور هم دانلود کنید** (با `scp` از سیستم خودتان) تا حتی اگر به خود سرور دسترسی را از دست دادید، یک نسخه جای دیگری داشته باشید:

```bash
# از روی سیستم خودتان (نه روی سرور):
scp user@YOUR_SERVER_IP:~/zagros-repost-backup-*.tar.gz ./
```

با این بکاپ، در بدترین حالت همیشه می‌توانید به وضعیت فعلی برگردید.

## مرحله‌ی ۱ — چک کردن پورت‌های آزاد (چون سرور مشترک است)

```bash
sudo ss -tulpn | grep LISTEN
```

یادداشت کنید چه پورت‌هایی الان اشغالند (احتمالاً پروژه‌ی قدیمی روی ۳۰۰۰ یا ۳۰۰۱ است — طبق `ecosystem.config.cjs` قدیمی چک کنید). برای این مرحله‌ی موقت تست، یک پورت کاملاً آزاد و بی‌ربط انتخاب کنید — مثلاً `3055` (اگر آزاد بود). این پورت را فقط برای تست موقت استفاده می‌کنیم، در پایان به پورت اصلی قدیمی برمی‌گردیم.

اگر مطمئن نیستید Postgres هم پورت پیش‌فرضش (`5432`) آزاد است یا نه:
```bash
sudo ss -tulpn | grep 5432
```
اگر همان سرور از قبل یک Postgres دیگر (برای سرویس دیگری) دارد، به‌جای پورت پیش‌فرض یکی دیگر (مثلاً `5433`) برای Postgres این پروژه انتخاب کنید — در مرحله‌ی بعد نشانتان می‌دهم کجا این را تنظیم کنید.

## مرحله‌ی ۲ — بالا آوردن Postgres جدا (تنها مورد جدید زیرساختی)

ساده‌ترین و امن‌ترین راه روی یک سرور مشترک: **یک کانتینر Docker تنها برای Postgres** — هیچ تداخلی با بقیه‌ی سرویس‌های سرور ندارد و بعداً هم راحت قابل حذف است.

اگر Docker از قبل نصب نیست:
```bash
curl -fsSL https://get.docker.com | sudo sh
```

بالا آوردن Postgres (پورت را با همان چیزی که در مرحله‌ی ۱ آزاد تشخیص دادید عوض کنید، پیش‌فرض این‌جا `5433` است تا با یک Postgres احتمالی دیگر روی سرور تداخل نکند):

```bash
docker run -d \
  --name zagros-repost-postgres \
  --restart unless-stopped \
  -e POSTGRES_USER=zagros \
  -e POSTGRES_PASSWORD='یک-رمز-طولانی-و-تصادفی-اینجا-بگذارید' \
  -e POSTGRES_DB=zagros_repost \
  -p 127.0.0.1:5433:5432 \
  -v zagros-repost-pgdata:/var/lib/postgresql/data \
  postgres:16-alpine
```

نکته‌ی مهم امنیتی: `-p 127.0.0.1:5433:5432` باعث می‌شود Postgres فقط از خود سرور در دسترس باشد (نه از اینترنت) — این را عوض نکنید.

چک کنید بالا آمده:
```bash
docker ps | grep zagros-repost-postgres
```

## مرحله‌ی ۳ — آپدیت ریپوی گیت‌هاب

این کار را از روی **سیستم خودتان** انجام می‌دهید (جایی که فایل zip نسخه‌ی جدید را از من گرفتید)، نه روی سرور:

```bash
# فایل zip را از حالت فشرده خارج کنید، بعد داخل همان پوشه:
cd zagros-repost-full   # یا هر اسمی که پوشه‌ی خارج‌شده دارد

git init   # فقط اگر این پوشه از قبل .git ندارد
git remote add origin https://github.com/USERNAME/REPO_NAME.git   # آدرس ریپوی قدیمی خودتان
# اگر remote از قبل تنظیم است، این خط را رد کنید یا remote را ست کنید:
# git remote set-url origin https://github.com/USERNAME/REPO_NAME.git

git add .
git commit -m "ارتقا به معماری جدید: Postgres، موتور push-based، تست خودکار، Docker، فیچرهای فاز ۳"
git branch -M main
git push origin main
```

اگر گیت از شما نام کاربری/رمز خواست، گیت‌هاب دیگر رمز عادی قبول نمی‌کند — باید یک [Personal Access Token](https://github.com/settings/tokens) بسازید و به‌جای رمز از آن استفاده کنید.

**نکته‌ی امنیتی مهم:** مطمئن شوید فایل `.env.local` (و `data/`) در `.gitignore` هستند و پوش نمی‌شوند — پروژه از قبل `.gitignore` درستی دارد، فقط قبل از `git add .` یک بار `git status` بزنید و مطمئن شوید هیچ‌کدام از این دو در لیست فایل‌های جدید نیستند.

## مرحله‌ی ۴ — نصب نسخه‌ی جدید کنار نسخه‌ی قدیمی (روی سرور)

```bash
cd /home/user   # یا هر مسیری که نسخه‌ی قدیمی هم آنجاست
git clone https://github.com/USERNAME/REPO_NAME.git zagros-repost-v2
cd zagros-repost-v2

npm install
npx prisma generate
```

### تنظیم `.env.local` نسخه‌ی جدید

```bash
cp .env.example .env.local
nano .env.local
```

مقادیر زیر را دقیقاً از `.env.local` **قدیمی** (از بکاپی که در مرحله‌ی ۰ گرفتید) کپی کنید — این‌ها باید همان مقدار قدیمی بمانند تا داده و دسترسی‌های موجود (توکن ربات‌ها و غیره) کار کنند:
- `GEMINI_API_KEY`
- `ADMIN_RECOVERY_KEY`
- `USERBOT_SECRET` (اگر یوزربات دارید)
- `USERBOT_RELAY_CHANNEL` (اگر دارید)

مقادیر زیر را **جدید** و مخصوص این نصب بگذارید:
- `DATABASE_URL="postgresql://zagros:همون-رمزی-که-در-مرحله-۲-گذاشتید@127.0.0.1:5433/zagros_repost"`
- `DATA_DIR="/home/user/zagros-repost-v2-data"` (یک پوشه‌ی تازه — بعداً حساب ادمین/session این‌جا ذخیره می‌شود؛ آن را از پوشه‌ی قدیمی جدا نگه دارید تا در این مرحله تداخلی رخ ندهد)

### اعمال migration ها و مهاجرت داده‌ی قدیمی

```bash
npx prisma migrate deploy
```

حالا داده‌ی پل‌ها/لاگ‌های قدیمی را از فایل JSON قدیمی به همین Postgres تازه منتقل کنید — به اسکریپت بگویید فایل‌های JSON قدیمی کجا هستند:

```bash
DATA_DIR=/home/user/zagros-repost/data npm run db:migrate-from-json
```

(مسیر `DATA_DIR` بالا باید به پوشه‌ی `data/` همان نصب **قدیمی** اشاره کند، نه نصب جدید — این فقط برای خواندن فایل‌های JSON قدیمی است، یک‌بار مصرف.)

خروجی این دستور تعداد پل‌ها/لاگ‌های منتقل‌شده را نشان می‌دهد — با تعداد واقعی پل‌های خودتان مقایسه کنید.

## مرحله‌ی ۵ — تست کامل نسخه‌ی جدید، جدا از نسخه‌ی قدیمی

```bash
npm run build
PORT=3055 node dist/server.cjs
```

(پورت `3055` را با همان پورت آزادی که در مرحله‌ی ۱ پیدا کردید عوض کنید.)

از سیستم خودتان یا با `curl` روی خود سرور تست کنید:
```bash
curl http://127.0.0.1:3055/api/auth/status
```

اگر فایروال اجازه می‌دهد، مرورگرتان را به `http://YOUR_SERVER_IP:3055` باز کنید. باید:
1. **صفحه‌ی لاگین را ببینید** (نه فرم ساخت حساب جدید — چون حساب ادمین قدیمی شما با همان username/password منتقل نشده؛ این یک محدودیت شناخته‌شده است، توضیحش پایین همین بخش).
2. بعد از حل مورد ۱، وارد پنل شوید و **پل‌های قدیمی خودتان را ببینید** (که از مرحله‌ی ۴ منتقل شدند).
3. یک ارسال تست از یکی از پل‌ها بزنید تا مطمئن شوید ارتباط با تلگرام درست کار می‌کند.

**⚠️ نکته‌ی مهم درباره‌ی حساب ادمین:** طبق تصمیم آگاهانه‌ی فاز ۱ نقشه‌راه (`references/roadmap.md`)، حساب ادمین و رمز عبور هنوز روی فایل JSON هستند نه Postgres — و چون `DATA_DIR` نسخه‌ی جدید را در بالا **عمداً جدا** از نسخه‌ی قدیمی تنظیم کردیم، صفحه‌ی اول یک فرم «ساخت حساب ادمین» نشان می‌دهد، نه لاگین. این طبیعی و مورد انتظار است — فقط یک‌بار با username/password جدید (یا همان قدیمی، فرقی نمی‌کند) دوباره حساب بسازید. اگر می‌خواهید حساب قدیمی دقیقاً حفظ شود، به‌جای این‌کار می‌توانید مستقیم `admin.json` قدیمی را کپی کنید:
```bash
cp /home/user/zagros-repost/data/admin.json /home/user/zagros-repost-v2-data/admin.json
```
(این را قبل از اولین بالا آمدن سرور جدید انجام دهید تا فرم ساخت حساب اصلاً نمایش داده نشود.)

با `Ctrl+C` سرور تست را متوقف کنید وقتی مطمئن شدید همه‌چیز درست کار می‌کند.

## مرحله‌ی ۶ — جایگزینی نهایی (این‌جا نسخه‌ی قدیمی متوقف می‌شود)

فقط وقتی از مرحله‌ی ۵ کاملاً مطمئن بودید این مرحله را انجام دهید.

```bash
# نام واقعی پروسه‌ی قدیمی را با pm2 list پیدا کنید
pm2 list
```

```bash
# پروسه‌ی قدیمی را متوقف کنید (اسمش را از خروجی بالا بگیرید، معمولاً zagros-repost)
pm2 stop zagros-repost
```

حالا `.env.local` نسخه‌ی جدید را ویرایش کنید و `DATA_DIR` را از پوشه‌ی تستی به همان پوشه‌ی داده‌ی اصلی/دائمی که می‌خواهید از این به بعد استفاده کنید تغییر دهید (یا همان مقدار قبلی تستی را نگه دارید — مهم این است که از این به بعد فقط همین یکی استفاده شود).

```bash
cd /home/user/zagros-repost-v2
pm2 delete zagros-repost 2>/dev/null   # اگر نام تکراری بود پاک شود
pm2 start ecosystem.config.cjs --name zagros-repost
pm2 save
```

بررسی کنید پورت درست است (`ecosystem.config.cjs` را باز کنید، `PORT` باید همان پورتی باشد که Nginx/فایروال قدیمی به آن اشاره می‌کند — معمولاً همان ۳۰۰۰ یا ۳۰۰۱ قدیمی، **نه** پورت تستی ۳۰۵۵).

اگر از Nginx استفاده می‌کنید و پورت backend عوض نشده، نیازی به تغییر تنظیمات Nginx نیست. اگر پورت را عوض کردید:
```bash
sudo nano /etc/nginx/sites-available/zagros-repost   # proxy_pass را به پورت جدید آپدیت کنید
sudo nginx -t && sudo systemctl reload nginx
```

آدرس دامنه/سرور را دوباره باز کنید و کامل تست کنید.

## مرحله‌ی ۷ — پاک‌سازی (فقط بعد از چند روز اطمینان کامل)

نسخه‌ی قدیمی را فوری پاک نکنید — چند روز صبر کنید تا از پایداری کامل نسخه‌ی جدید مطمئن شوید. بعد از آن:

```bash
# فقط پروسه‌ی pm2 قدیمی که متوقف شده را کامل حذف کنید (اگر جدا از جدید بود)
pm2 delete zagros-repost-old 2>/dev/null

# پوشه‌ی کد قدیمی را می‌توانید حذف کنید — بکاپ فشرده‌ی مرحله‌ی ۰ کافی است
# rm -rf /home/user/zagros-repost   # این خط را عمداً کامنت گذاشتم؛ فقط وقتی صد‌درصد مطمئن بودید خودتان کامنتش را بردارید
```

## اگر یوزربات (موتور push-based فاز ۲) هم می‌خواهید فعال کنید

این کاملاً اختیاری و جدا از مراحل بالاست — بعد از اینکه نسخه‌ی جدید پایدار شد، در یک زمان دیگر انجامش بدهید:

1. `TELEGRAM_API_ID` و `TELEGRAM_API_HASH` را از https://my.telegram.org بگیرید.
2. در `.env.local` نسخه‌ی جدید اضافه کنید.
3. یک‌بار (تعاملی، نیاز به کد پیامکی): `cd userbot && pip install -r requirements.txt && python3 login.py`
4. سرویس را دائمی اجرا کنید: `NODE_WEBHOOK_URL=http://127.0.0.1:PORT pm2 start userbot_service.py --interpreter python3 --name zagros-userbot` (PORT همان پورت اصلی برنامه‌ی Node است).
5. `pm2 save`
